# Stamp Matcher App Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** An installable, offline phone web app (PWA) in which the father photographs album pages to build his collection, checks a stamp at the club against it, files new stamps, and backs everything up.

**Architecture:** React screens on the main thread; OpenCV.js and the DINOv2 model run in one Web Worker behind a small RPC (`Recognizer`), reusing `src/core`. All data lives in IndexedDB on the phone (`src/db`). Pure decision logic (what to do with a re-photographed page, whether two stamps' edges differ, snapping a box to a tap) lives in `src/core` and is unit-tested in Node. Static build deployed to GitHub Pages.

**Tech Stack:** TypeScript, Vite 5, React 18, `vite-plugin-pwa` (Workbox), `idb`, `fflate` (backup zip), Vitest + `@testing-library/react` + `jsdom` + `fake-indexeddb`; existing `@techstark/opencv-js`, `@huggingface/transformers`.

**Spec:** `docs/superpowers/specs/2026-11-20-stamp-matcher-design.md` (incl. "Decisions from the recognition trial"); evidence in `docs/superpowers/trial-results.md`.

## Global Constraints

- UI language **Russian by default, switchable to English**; every visible string goes through `t(key)`; both dictionaries must have every key (a test enforces it).
- Works fully **offline** after first load (app shell, OpenCV, model all cached). No server, no accounts, no network calls besides the one-time model download.
- All user data stays on the device in IndexedDB; call `navigator.storage.persist()` on first run.
- Model: `Xenova/dinov2-small`, dtype `q8`; matching `colorWeight: 0.5`, top **5**.
- Never a bare yes/no: the check screen always shows candidate images.
- Never silently drop or merge a stamp: every "already saved" / "this is your unfiled stamp" outcome is a **proposal the user confirms**.
- Large touch targets (min 48 px), base font ≥ 18 px — the user is older and not technical.
- `test-photos/` and `trial-output/` stay git-ignored.
- `src/core` stays browser-compatible (no Node imports).

## Review Focus

1. **Huge camera photos (12–50 MP) on a mid-range phone** — decoding must downscale (≤ 3000 px longer side) before detection so the tab doesn't crash (test in Task 4).
2. **The browser evicts storage / user reinstalls** — backup export→import must round-trip every field, including embeddings and images (test in Task 10).
3. **Re-photographing a page that already has duplicates (two copies of one stamp)** — both copies must be proposed as "already saved" separately, never one merged (test in Task 3).
4. **Model download interrupted (offline on first run)** — the app must show a retry message, and a later retry must work (failed load must not be cached) (test in Task 4).
5. **Album/page entered as text with spaces or leading zeros ("03 ")** — stored as the number 3, so the page is found again (test in Task 6).

### Task 3: Page save plan (pure logic)

**Files:**
- Create: `src/core/savePlan.ts`
- Test: `src/core/savePlan.test.ts`

**Interfaces:**
- Consumes: `rankMatches`/`colorSimilarity` math from `src/core/match.ts` (`score = 0.5*cosine + 0.5*colour`)
- Produces:
  ```ts
  export type Candidate = { tempId: string; pos: NBox; embedding: Float32Array; color: Float32Array };
  export type Known = { id: string; pos?: NBox; embedding: Float32Array; color: Float32Array };
  export type NBox = { x: number; y: number; w: number; h: number }; // normalized
  export type Proposal =
    | { tempId: string; type: 'new' }
    | { tempId: string; type: 'alreadySaved'; itemId: string; score: number }
    | { tempId: string; type: 'fileUnfiled'; itemId: string; score: number };
  export function planPageSave(cands: Candidate[], onPage: Known[], unfiled: Known[]): Proposal[];
  export const ALREADY_MIN_IOU = 0.5, ALREADY_MIN_SCORE = 0.5, UNFILED_MIN_SCORE = 0.6, UNFILED_MIN_MARGIN = 0.03;
  ```
  Rules: (1) `alreadySaved` when an on-page item overlaps (IoU ≥ 0.5) **and** scores ≥ 0.5; (2) otherwise `fileUnfiled` when the best unfiled item scores ≥ 0.6 and beats the second-best unfiled by ≥ 0.03; (3) otherwise `new`. Each known item is used by at most one candidate — assign greedily by descending score. Output order = input order.

- [ ] **Step 1: Write failing tests** (unit vectors built by hand):
  - candidate identical to an on-page item at the same position → `alreadySaved` with that id.
  - same image but IoU 0.2 (moved to another spot) and no unfiled match → `new`.
  - **two identical copies on the page, two identical candidates at their two positions → two `alreadySaved` with two different item ids** (Review Focus 3).
  - candidate matching an unfiled item at 0.9 with runner-up 0.5 → `fileUnfiled`.
  - two unfiled items both at ~0.9 (margin < 0.03) → `new`.
  - two candidates both best-matching one unfiled item → only the higher-scoring gets `fileUnfiled`, the other `new`.
- [ ] **Step 2:** Run — FAIL. **Step 3:** Implement. **Step 4:** Run — PASS.
